# c9p/1 protocol

## Frames

The Unix transport is UTF-8 NDJSON: one JSON object and one newline per frame. The gateway uses one JSON object per WebSocket text message, without a newline. It needs M-b.

A request has `v:1`, a unique string `id`, a `method` and `params`. A write may also accept an `idem` key. The SDK never retries a write automatically. Reusing an id on one connection is invalid.

```json
{"v":1,"id":"2","method":"session.views","params":{}}
```

A success has `v`, the same `id`, `ok:true` and `result`. Some writes include `seq`, the cursor of their committed event. A failure has `ok:false` and `error:{code,msg,retryable,hint,data?}`. An event has `type:"event"`; `sub` is the subscription request id. Responses do not have `type:"event"`. A conversation request may produce `type:"progress"` frames with its request id when the client asks for `conversation.progress` in `hello.want`.

Responses on one connection may arrive out of order. Match each response to its request by `id`, not by arrival order. Core handles the requests on one connection concurrently, at most 32 at a time; past that it reads no more frames until one ends. A `events.subscribe` response still comes before the first event of its stream, and no event of a stream comes after its `events.unsubscribe` response.

`idem` makes a write safe to resend. A second request from the same principal with the same `idem` and the same params replays the original result and does not repeat the write. The same `idem` with other params is `duplicate`. `msg.send`, `agent.create`, `agent.retire` and `session.stop` support `idem`. Only a success is kept: after a failure, a resend with the same `idem` runs the write again. Concurrent requests with one `idem` run the write once. `msg.send` keeps its key with the message. The other three keep it in core's memory for 24 hours, for at most 1024 keys. `idem` keys are kept for the life of one engine process; after a restart a repeated key runs again. A key that a request still uses is never dropped; when all 1024 keys are in use, a new key gets `busy`. An `idem` is 1 to 128 bytes.

Clients ignore unknown fields. Clients accept unknown state, status, role, mode, control and source strings. Do not treat a new string as a parse failure. Do not use a connection after a malformed frame or a major mismatch.

Some agent states are reserved. `refreshing` and `retiring` are in the schema, but core does not emit them today. Clients must accept them.

## Agent lifecycle

`orphaned` means that no kill could confirm that the agent's process ended. Core writes it from c9p 1.11 (upcoming). A kill sends SIGTERM, waits up to 3 s, sends SIGKILL, and waits up to 2 s more. Core signals a process only while it still has the recorded pid and start time, so a reused pid is never signalled. If the exit is still not confirmed, the row becomes `orphaned` with `stateReason` `kill_unconfirmed`, and core writes an audit row. An `orphaned` agent:

- is not resumable, by a boot or by `agent.resume`;
- keeps `goneAt` `null`, because its process may still run, and counts as live for the cwd rules of `agent.create` (`cwd_collision`);
- leaves `orphaned` only by `agent.retire`, which kills again by pid and start time. When that kill is confirmed, the row becomes `retired`. Otherwise the row stays `orphaned`.

Core records the processes that an unconfirmed kill left, up to 64. A retire kills the recorded process and each of these again, and the row becomes `retired` only when every one is confirmed gone. If the kill left more than 64, core cannot confirm the rest. The row then stays `orphaned` with `stateReason` `survivors_overflow`, even after the recorded ones are gone.

`agent.retire {id, force: true}` (c9p 1.11, upcoming, local client only) ends an `orphaned` agent that no kill can confirm. Core kills by pid and start time as usual, then writes the tombstone and an audit row (`agent.retire`, decision `forced`) that says what may still run. Like `agent.retire` itself, `force` is for the local client only: any other principal gets `not_allowed` before `force` is read. `force` has no effect on an agent that is not `orphaned`.

`agent.retire` returns the tombstone (`retired`) when the kill is confirmed or forced, and the `orphaned` row when it is not.

`agent.resume {id}` (c9p 1.11, upcoming, local client only) resumes a `paused` or `interrupted` engine agent on its session. It answers with the agent when it is `ready`. A failed resume does not end the agent. The row goes back to `paused` or `interrupted` with `stateReason` `resume_failed`, and the error says why (`spawn_failed`, with the vendor's text). Call `agent.resume` again to retry. So a `paused` or `interrupted` agent with `stateReason` `resume_failed` means that its last resume failed and `agent.resume` can retry it. The failure text is in the `agent.resume` error and in the audit row (`agent.resume`, decision `failed`).

An `orphaned` row and a `paused` or `interrupted` row with `resume_failed` keep `goneAt` `null`, so they count as live engine agents. While one exists, `agent.create` in another cwd, or in a cwd above or below its cwd, fails with `cwd_collision`. A create in its own cwd is allowed. Call `agent.retire` on that agent to clear it.

Boot behavior changes in 1.11. A boot resumes `paused` agents with reason `drain` and `interrupted` agents, but it skips every row with `resume_failed`. Before 1.11, a failed boot resume ended the agent as `failed`. Now the row waits for `agent.resume` or `agent.retire`, and it counts as live for the cwd rules of `agent.create`.

Only one resume of an agent runs at a time. `agent.resume` returns `action_failed` when the agent is not `paused` or `interrupted`, already runs, is `orphaned`, or has no session to resume. It returns `not_allowed` for every principal except `local-unverified`.

## Hello and discovery

`hello` must be the first request. `hello` never waits for session detection. While core starts, before detection's first successful pass, the principal `hello` reports is provisional: it may say `local-unverified` for a process that is inside an observed session. Core stamps the connection again before its first request that needs the caller's identity (a write, `session.stop`, a method or topic that an observed session may not use, such as `msg.*` reads or `legacy.inbox`), and keeps that result; from then on the principal may be `observed:<sessionKey>`. That request waits up to 3 s for detection; past that it gets `busy` with its own `id`, and the connection stays open. If core cannot verify the connection's process at that point (it exited, or its start time is unreadable), every request that needs the caller's identity gets `peer_not_authorized`; connect again. Other reads answer at once. If detection never succeeds, restricted requests keep returning busy; check detect.health. Send `params.apiMajor:1` and the minor your client was built against in `params.apiMinor`. `client` is a label, never an authorization claim. `want` is a list of feature tokens you understand. The returned `capabilities` is their supported intersection.

The result includes:

| Field | Meaning |
| --- | --- |
| `apiMajor`, `apiMinor` | Core's protocol version |
| `engineVersion`, `machineId` | Core build and machine identity |
| `principal` | Identity stamped from connection facts |
| `stability` | `preview` |
| `methods` | Method name to `{since,rev,stability}` |
| `breakingSince` | Methods with a breaking preview revision after your build minor |
| `topics` | Event topic names |
| `limits` | Frame, stream, connection and retention limits |
| `cursor` | Current event log head |

`since` is the minor that introduced the method. `rev` starts at 1 and rises on a breaking shape change. Refuse a method in `breakingSince` and update the client. A breaking changelog entry must say **breaking (preview)** and give the new method revision. An absent method is unsupported. A listed method can still be unauthorized.

In 1.6, socket discovery includes internal methods and topics. Use only the public schema. M-b narrows discovery by principal and adds `needs:{scopes,ceiling?}` for methods that need more access. It also supplies `auth.can` and `auth.rules`; they are not in 1.6.

A major mismatch returns `upgrade_required` and closes the connection. Stable breaking changes will require a new major and a new socket name, such as `engine-v2.sock`.

## Principals and access

Core derives `local-unverified`, `agent:<id>` or `observed:<sessionKey>` from the Unix peer. `observed:<sessionKey>` is a process inside a session that core observes but did not create, for example a Bash tool of your own Claude Code session. It reads as `local-unverified` does. It may send mail, and the message names the session as its source. It may stop only its own session. It may not call `agent.create`, `agent.retire`, `session.rename`, `detect.recheck`, the mailbox reads or the mailbox controls. Its annotations go under its own `observed.<hash>` namespace. A same-user socket is a local trust boundary. `hello.client` cannot turn a script into a trusted agent. `hook.*`, `task.done` and `agent.handoff` are private; they require core's own agent binary and are absent from public export and SDK calls.

Gateway connections will receive `client:<id>` only after token verification. They use scopes and a sensitivity ceiling. See [gateway.md](gateway.md). The public schema is a documentation surface, not a grant. Every request must still pass core's access checks.

## Query, subscribe, resume

1. Read `session.views {}`. It returns `{cursor,sessions}`.
2. Store the sessions by `sessionKey`.
3. Call `events.subscribe {since:cursor,topics:["session.view","session.gone"]}`.
4. Apply each event. Persist its cursor only after processing succeeds.
5. On reconnect, repeat `hello` and subscribe with `since` set to the last completed cursor.

`topics` accepts exact names and suffix wildcards such as `agent.*`. `subjects` accepts exact subject strings. Empty filters match all available events. With no `since`, a subscription starts at the current head and has no replay. `events.unsubscribe {sub}` ends it. Closing the connection ends all its streams.

`seq` increases within an epoch, but it can have gaps. Compaction deletes older `session.view` events. Do not infer a lost event from a gap in `seq`. Only `cursor_expired` means events are missing.

A cursor belongs to one machine and one database epoch. Treat it as opaque in clients. `cursor_expired` means it is pruned, from another machine or epoch, or ahead of the log. Read a fresh query snapshot and replace local state before subscribing again. Never silently reset a resume cursor to the current head.

Retention is **24 hours or 50,000 events**, whichever comes first. Use `hello.limits` for the actual server values. `session.view` is a latest-state topic: stored views are compacted. Replay can give only the newest view of a live session; it cannot reconstruct every status transition. Live subscribers see views as core writes them. Use [topics.md](topics.md) for the distinction.

History uses `page:{offset,limit}`. Follow `nextOffset` until it is null. Pages can be shorter than `limit` because core applies a byte budget. History is read anew for each page; exports are not a transaction across provider files. A row with `truncated:true` contains an omission note for oversized content.

## Detector health (1.11)

A failed detection pass writes nothing. The session rows then keep what the last good pass saw. An empty or unchanged list is therefore not proof that the machine is quiet. Check the detector's health before you show the list as live.

- `snapshot.get` and `session.list` add `observedAt`: the Unix ms of the last detection pass that core wrote. They also add `detectorHealth`, a `DetectorHealth`. Both fields are absent when the engine runs no detection.
- `DetectorHealth.state` is `ok`, `degraded`, `failed` or `starting`. Accept other values. `degraded` means some providers did not answer; `failedProviders` names them, and their rows keep older data. `failed` means the last pass wrote nothing; `reason` says why.
- `stale` is true when no pass was written for `staleAfterMs` (30 000 today). Then treat every detected row as out of date. Rows of a provider in `failedProviders` can be out of date while `stale` is false.
- `observedAt` equals `detectorHealth.lastOkAt`. Core reads the health before the rows, so a pass that commits in between makes the rows newer than `observedAt`, never older.
- Topic `detect.health` (subject: machine id) carries a `DetectorHealth` when `state`, `failedProviders` or `stale` changes. A change of `reason` alone emits nothing.
- While passes are written, core repeats `detect.health` every `staleAfterMs / 2` (15 s today) with a newer `lastOkAt`, and not more often. So a client can age `lastOkAt` by its own clock: past `staleAfterMs` with no newer event, treat the data as stale. A failing or hung detector sends no heartbeat.

## Errors and limits

Use `error.code` for decisions, `msg` and `hint` for display, and `retryable` for retry policy. Preserve an unknown code in the error shown to the caller. Codes include `bad_request`, `unknown_method`, `upgrade_required`, `peer_not_authorized`, `not_allowed`, `cursor_expired`, `busy` and `internal`. Operations the engine does not implement yet return `unsupported`.

The socket reads at most 1 MiB per frame and accepts at most 64 connections, with 16 streams per connection. `hello` has a 5-second deadline. Conversation and history pages use a smaller byte budget. The SDK bounds incoming frame size, pending call time and event callbacks waiting to run. A slow consumer must resnapshot if it cannot stay within retention.

`ping {}` returns `{ts}` for liveness. A live socket alone is not proof that queries or subscriptions are healthy.

The exact params and results are in `c9watch api schema --public`. These groups cover the public surface:

| Methods | Use |

Public means documented. It does not mean callable by every principal.
